# NanoTTS

Продакшен-инференс на CPU для небольших речевых моделей:
[Kyutai **Pocket TTS**](https://huggingface.co/kyutai/pocket-tts) с его
файн-тюнами и семейство **Supertonic 3** (сам Supertonic 3 и TeraTTS v2).
Производная от [VolgaGerm/PocketTTS.cpp](https://github.com/VolgaGerm/PocketTTS.cpp)
(MIT), переписанная под многопоточное обслуживание, NUMA-локальность и
OpenAI-совместимый HTTP API.

Эти модели достаточно малы, чтобы быть по-настоящему быстрыми на процессоре, и
вот что нужно, чтобы их обслуживать: прогретые голоса, стартующие с `memcpy`,
stateless-графы ONNX, веса, реплицированные по NUMA-нодам, и отдача с первого
кадра.

Ниже ватерлинии у двух архитектур нет почти ничего общего — одна авторегрессивна
поверх кодека на 12.5 Гц, другая оценивает длину фразы и решает её одним
проходом flow-matching, — поэтому они стоят за интерфейсом бэкенда. HTTP API,
стриминг, форматы, раскладка по NUMA, метрики и консоль общие; остальное
выбирается полем `architecture` в манифесте бандла.

```bash
curl -fsSL https://raw.githubusercontent.com/usunrise88/NanoTTS/main/install.sh | bash
```

## Установка

Однострочник выкачивает исходники, экспортирует чекпоинт в ONNX, собирает образ
и поднимает сервис на `127.0.0.1:8080`. Всё работает в Docker; на хост кладутся
только один каталог и запускалка `nanotts`.

```bash
# базовый язык Pocket TTS вместо русского файн-тюна по умолчанию
curl -fsSL .../install.sh | bash -s -- --model english

# открыть наружу, выбрать порт, остаться на fp32
curl -fsSL .../install.sh | bash -s -- --bind 0.0.0.0 --port 9000 --precision fp32

curl -fsSL .../install.sh | bash -s -- update
curl -fsSL .../install.sh | bash -s -- uninstall           # голоса сохраняются
curl -fsSL .../install.sh | bash -s -- uninstall --purge    # удалить и голоса
```

Дальше: `nanotts start | stop | restart | status | logs | update | uninstall`.

```bash
# чекпоинт из второго семейства
curl -fsSL .../install.sh | bash -s -- --model TeraSpace/TeraTTSv2
```

Требования: Linux x86_64 (крайне желателен AVX2), Docker с Compose v2, git и
около 12 ГиБ диска — большая часть под экспорт в ONNX, который модели s3
пропускают, потому что выпущены уже графами.

## Модели

### Pocket TTS и его файн-тюны (`architecture: pocket`)

Всё, что умеет загружать пакет `pocket-tts`, потому что экспорт идёт через
`TTSModel.load_model`:

| `--model` | Что это |
|---|---|
| `english`, `english_2026-04`, `english_2026-04_24l` | база Kyutai, английский |
| `french_24l`, `german`, `german_24l`, `italian`, `italian_24l` | база Kyutai |
| `portuguese`, `portuguese_24l`, `spanish`, `spanish_24l` | база Kyutai |
| `genvoice/xVibePocketTTS` | русский файн-тюн — по умолчанию |
| `owner/name` | любой репозиторий HuggingFace с `config.yaml` |
| `hf://…`, `https://…`, `/path/to/config.yaml` | передаётся как есть |

Геометрию рантайм читает из манифеста экспорта — число слоёв, головы, размерность
латента, частоту кадров, — поэтому 24-слойные варианты работают ровно так же, как
6-слойные.

### Supertonic 3 и TeraTTS v2 (`architecture: s3`)

| `--model` | Что это |
|---|---|
| `TeraSpace/TeraTTSv2` | русский и английский, 44.1 кГц, десять готовых голосов |
| `Supertone/supertonic-3` | английский, корейский, японский, 44.1 кГц |

Эти две выпущены как ONNX, а не как веса, поэтому трассировать нечего: установка
скачивает графы и конвертирует голоса. Архитектура у них общая — интерфейсы
графов совпадают вплоть до форм тензоров, различается одно имя выхода, — а вот
текстовые соглашения разные, и они живут в манифесте, а не в коде.

От Pocket TTS они отличаются двумя вещами, которые важнее формата файлов:

- **TTFB растёт с длиной текста.** Предиктор длительности оценивает фразу
  целиком, один проход flow-matching заполняет её всю, и до этого не слышно
  ничего; стримится только вокодер. Pocket TTS отдаёт первый кадр сразу и к
  длине текста безразличен. Замерено на базовой машине: 564 мс на фразе из трёх
  слов, 755 мс на фразе из десяти — против ровных ~171 мс у Pocket без ударений.
- **Клонирования голоса нет.** В релизах лежат фиксированные стилевые векторы и
  нет энкодера стиля, поэтому `POST /v1/voices` отвечает 501 и объясняет почему.
  Доступны те голоса, что пришли с чекпоинтом.

У TeraTTS вдобавок словарь из 134 символов без цифр, поэтому числа разворачиваются
в слова до попадания в энкодер: неразвёрнутая цифра не произносится неправильно —
она исчезает вместе со смыслом. Числитель сверен с num2words на 382 случаях из
382, включая согласование родов в русском.

**Все замеры ниже сделаны на русском файн-тюне Pocket.** Остальные чекпоинты
проходят через тот же код, но их числа приводить не нам.

## Что внутри

- **HTTP-сервер** с эндпоинтом `/v1/audio/speech`, потоковой отдачей (chunked),
  форматами `wav` / `pcm` / `mp3`.
- **Веб-консоль** для проверки: синтез, мониторинг и загрузка своих голосов там,
  где модель умеет их выучивать. Вшита в бинарь.
- **NUMA-раскладка**: по движку на ноду, веса реплицированы, потоки запинены,
  память аллоцируется локально.
- **Два бэкенда** за одним интерфейсом, выбор по полю `architecture` в манифесте.
  Всё, что выше этой линии, общее.
- **Ударения** через сайдкар RUAccent для русского, и ими пользуются обе
  архитектуры: Pocket ждёт комбинирующий акут, s3 — `+` перед гласной, а клиент
  пишет как удобно. Без ударений русский чекпоинт Pocket даёт 17.7% WER
  вместо 3.2%.

Чем они на самом деле различаются:

| | `pocket` | `s3` |
|---|---|---|
| устройство | авторегрессия поверх кодека 12.5 Гц | предиктор длительности + один проход flow-matching |
| TTFB | не зависит от длины текста | растёт с ней |
| голоса | префилл KV-кэша, клонируется с WAV | фиксированные стилевые векторы, не клонируется |
| графы | пять, экспортируются из весов | четыре, поставляются как ONNX |
| выход | 24 кГц | 44.1 кГц |

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/audio/speech` | синтез; `input`, `voice`, `response_format` и объект `nanotts` с доп. параметрами |
| GET | `/v1/models`, `/v1/voices` | каталоги |
| POST | `/v1/voices` | multipart `id` + `file` (WAV) → прогрев → `.safetensors`; **501** там, где архитектура не умеет клонировать |
| GET | `/v1/voices/{id}/state` | скачать прогретое состояние |
| DELETE | `/v1/voices/{id}` | удалить голос |
| GET | `/v1/registry` | что установлено, что можно скачать, что качается |
| POST | `/v1/registry/install` | `{"id": "TeraTTSv2"}` → запускает загрузку, возвращает задачу |
| POST | `/v1/registry/{id}/activate` | переключить работающий сервер на эту модель |
| DELETE | `/v1/registry/{id}` | удалить установленную модель |
| GET | `/healthz`, `/readyz`, `/stats`, `/metrics` | эксплуатация |

```bash
curl -X POST localhost:8080/v1/audio/speech -H 'Content-Type: application/json' -d '{
  "input": "Ст+арый з+амок сто+ит д+орого, а дв+ерь закрыв+ает зам+ок.",
  "voice": "male_deep",
  "response_format": "wav",
  "nanotts": {"temperature": 0.5, "eos_threshold": -4.0, "seed": 42}
}' --output out.wav
```

Дополнительные параметры лежат в отдельном объекте, чтобы OpenAI-клиент, который
о них не знает, продолжал работать. Там же принимается `xvibe` как синоним
`nanotts` — так этот объект назывался до переименования проекта.

## Переключение моделей на ходу

Запущенный с `--models DIR` сервер держит там реестр, а в консоли появляется
страница «Модели»: видно установленное, чекпоинт скачивается по требованию с
прогрессом, и работающий сервер переключается на него.

Переключение пересобирает все воркеры под новый бандл и занимает около секунды.
Сначала оно дожидается простоя — бэкенд нельзя вынуть из-под запроса, который
на середине фразы, — и строит новые движки до того, как разбирать старые, чтобы
негодный бандл упал, пока предыдущая модель ещё отвечает. Замерено на трёх
воркерах при смене архитектуры: 1.1–1.3 с, после чего `/v1/models` отдаёт новую
частоту дискретизации и признак того, умеет ли модель клонировать голос.

Скачиваются только чекпоинты, выпущенные как ONNX, — та же граница, что и везде:
модель Pocket TTS нужно трассировать из весов, а Python для этого в образе
сервиса сознательно нет. API так и отвечает, вместо невнятного отказа.

```bash
curl -X POST localhost:8080/v1/registry/install \
  -H 'Content-Type: application/json' -d '{"id":"TeraTTSv2"}'
curl localhost:8080/v1/registry            # следить за задачей
curl -X POST localhost:8080/v1/registry/TeraTTSv2/activate
```

## Порог EOS

Дефолт — **−4.0**, как в самой `pocket-tts`. На карточке GenVoice `EOS −1` указан
как условие их бенчмарка, и взять это значение за рабочий дефолт оказалось дорого:
при −1.0 модель регулярно дочитывает текст и продолжает говорить отсебятину
несколько секунд. Измерено на одних сидах:

| набор | −1.0 | −4.0 |
|---|---|---|
| короткие фразы (20) | WER 5.59% / CER 1.60% | 6.21% / 1.70% |
| длинные фразы (8) | 5.65% / 2.14% | **4.84% / 2.03%** |
| длинный абзац, 6 сидов | 16.20% / 9.68% | **9.72% / 2.94%** |

Проседание на коротком наборе — одна фраза из двадцати: четыре из пяти ошибок
совпадают между порогами, и ни одна не является обрывом концовки. Падение CER
втрое на длинном абзаце — это ровно исчезнувший хвост отсебятины.

Сверх порога длина генерации чанка ограничена как в апстриме —
`ceil((токенов/3 + 2) × 12.5)` кадров. Без этого пропущенный EOS болтал до
`max_frames`, то есть до сорока секунд.

## Ударения (русский)

Чекпоинт обучен на тексте с U+0301, и без ударений качество рушится. Измерено на
одних сидах с прогоном через ASR:

| набор | без ударений | RUAccent | ручные ударения |
|---|---|---|---|
| длинные фразы (8) | WER 17.74% | **3.23%** | 3.23% |
| обычный набор (20) | WER 20.50% | **6.21%** | 9.32% |

RUAccent обыгрывает и ручную разметку. Он живёт отдельным сайдкаром (`accent/`),
потому что это Python без нативного порта; модели вшиты в образ, так что старт не
требует сети. Подключается флагом `--accent-url`; без него сервер ударения не
ставит и ждёт их от клиента.

Цена — задержка: TTFB 171 → ~300 мс p50 на обычной прозе, до ~650 мс на тексте,
насыщенном омографами. Распределение бимодальное: обычное предложение
размечается за 30–60 мс, предложение с омографом — около 600 мс, потому что
включается модель разрешения. Смягчается кэшем по тексту, четырьмя ONNX-потоками
на экземпляр (медиана 102 → 59 мс) и тем, что сайдкару отдана собственная
NUMA-нода: без изоляции он отнимал ещё около 180 мс.

На критическом пути размечается только столько текста, сколько нужно первому
чанку. Разрез идёт **по границам предложений**, а чанкинг — уже после разметки,
поэтому границы чанков те же, что были бы без конвейеризации. Обратный порядок
(сначала чанкинг, потом разметка кусков) дешевле, но неверен: бюджет токенов
пришлось бы занижать под будущие U+0301, а это ломает длинные предложения по
запятым там, где модель прочитала бы их слитно.

Ручные ударения всегда в приоритете: `+` перед гласной или U+0301 после неё.
Такие слова подменяются плейсхолдерами перед вызовом RUAccent и возвращаются как
есть. Избыточные метки с «ё» снимаются, а `+` остаётся литералом там, где за ним
не русская гласная, так что `C++` и `2+2` не ломаются. На запрос отключается
через `"nanotts": {"auto_accent": false}`.

## NUMA

Базовая машина — EPYC 7351P: один сокет, но **четыре NUMA-ноды** по 4 ядра и
32 ГБ, и восемь CCX по 8 МБ L3. Удалённое обращение стоит 16 против 10 локального,
поэтому веса реплицируются по нодам (int8-бандл ~110 МБ, четыре копии — 440 МБ из
128 ГБ), а не шарятся.

```
--nodes 0,1,2,3        какие ноды занять (по умолчанию все)
--workers-per-node N   несколько движков на ноду; ядра делятся между ними
--threads N            intra-op потоков на движок (по умолчанию — физических ядер)
--smt                  использовать и SMT-сиблинги
--no-pin               без пиннинга и привязки памяти (для контейнеров без CAP_SYS_NICE)
```

Порядок важен: поток-создатель сначала пинится и переключает политику памяти на
`MPOL_BIND`, и только потом создаются сессии ORT — иначе first-touch разложит
веса не туда. Потоки ORT привязываются через `session.intra_op_thread_affinities`.

`nanotts topology` печатает обнаруженную раскладку.

## Замеры

EPYC 7351P, один воркер на ноду, int8, 20 фраз, governor `schedutil`:

| Конкурентность | Пропускная способность | TTFB p50 | TTFB p95 | RTF p50 |
|---|---|---|---|---|
| 1 | 4.03× realtime | 171 мс | 192 мс | 0.251 |
| 4 | 9.02× realtime | 268 мс | 374 мс | 0.423 |
| 8 | 8.94× realtime | 2029 мс | 2723 мс | 0.848 |

Насыщение наступает на числе одновременных запросов, равном числу воркеров: сверх
этого запросы встают в очередь. Снять этот потолок должен континуальный батчинг —
графы для него уже экспортированы (см. ниже), планировщик ещё нет.

```bash
export ASR_KEY=...
python3 tools/bench/bench.py --url http://localhost:8080 --voice male_deep --seed 1000 \
  --concurrency 4 --asr-url http://asr-host/v1 --asr-key "$ASR_KEY"
```

## Устройство экспорта pocket

Чекпоинты s3 поставляют графы готовыми, поэтому раздел только про Pocket TTS;
остальные скачивает и описывает `tools/export/fetch_s3.py`.

Пять графов, все stateless — состояние ходит через входы и выходы:

| Граф | Роль |
|---|---|
| `flow_lm_main` | AR-остов, split K/V кэш в fp16, голова EOS |
| `flow_lm_flow` | один шаг LSD-солвера: `(c, s, t, x) → flow_dir` |
| `text_conditioner` | токены → эмбеддинги |
| `mimi_encoder` | аудио → 1024-мерное обусловливание (`speaker_proj` вшит) |
| `mimi_decoder` | латенты + состояние → аудио |

Два отличия от экспорта PocketTTS.cpp:

- **`step` — вектор `[B]`, а не общий скаляр**, и RoPE берёт пер-строчное
  смещение. Строки независимы, слот может стоять на любой позиции. Это даёт
  настоящий континуальный батчинг вместо когорт в локстепе и убирает нужду в
  `pad`-выравнивании апстрима. Проверено: две строки на позициях 41 и 17 в одном
  батче дают **побитово** тот же результат, что независимые прогоны.
- **Один общий `step` вместо послойных**: 13 тензоров состояния вместо 18.

Контракт: референсное аудио для энкодера должно быть кратно 1920 сэмплам — граф
трассируется frame-aligned, иначе в него запечётся ненулевой паддинг. Рантайм
добивает сам.

## Референс для клонирования (pocket)

Выучить голос с записи умеет только авторегрессивное семейство; чекпоинты s3
приходят с фиксированными стилевыми векторами и отклоняют загрузку.

Сервер измеряет загруженный WAV и сохраняет его рядом с голосом вместе с отчётом:
длительность, пик, уровень речи, DC, клиппинг, доля тишины, crest-фактор. Прогрев
всегда «успешен» — энкодер одинаково охотно кодирует речь и шум, — поэтому без
этого замера плохой клон не оставляет улик.

Измерено на 20 фразах с прогоном через ASR: поставляемое GenVoice состояние 9.32%
WER, прогрев из того же аудио 8.70%, живая запись 44.1 кГц 13.04%. Длительность
сама по себе почти не влияет (4.4 с чистой записи дают 10.56%), тишина по краям
безвредна, а низкий уровень стоит около шести пунктов.

## Ограничения

- **Батчинг не реализован**, хотя графы его поддерживают и это проверено.
  Потолок — число воркеров.
- **Цена int8 не определяется по WER.** int8 даёт RTF 0.35 → 0.25, а вот его цена
  в качестве на этих наборах тонет в шуме. Три базы сидов, WER:

  | | короткие (20) | длинные (8) |
  |---|---|---|
  | int8 per-tensor | 6.21 · 6.21 · 8.07 → 6.83% | 4.84 · 4.03 · 2.42 → 3.76% |
  | int8 per-channel | 6.83 · 11.18 · 7.45 → 8.49% | 1.61 · 5.65 · 0.81 → 2.69% |
  | fp32 (один сид) | 7.45% | 4.03% |

  Разброс между сидами на одном наборе доходит до пяти пунктов — больше, чем любая
  разница между вариантами, — и направление меняется от набора к набору. Более
  ранняя запись «int8 стоит 1.9 п.п. WER» опиралась ровно на одну такую пару и не
  воспроизводится. Чтобы ответить на вопрос, нужен корпус масштаба GenVoice
  (800 генераций), а не 28 фраз.

  Важнее другое: **WER здесь вообще не тот инструмент.** ASR расшифровывает фразу
  сквозь тембровые артефакты, поэтому повреждение звука он не видит, а слушатель
  слышит сразу. Сравнение сгенерированного звука с fp32 тоже не работает — цикл
  авторегрессивный, отличие в первом кадре уводит траекторию, и на выходе две
  разные реализации фразы, а не эталон и копия (SNR −1.8 дБ, то есть
  некоррелированы).

  Мерить надо графы напрямую: 600 кадров с teacher forcing, всем вариантам
  подаётся один и тот же fp32-латент, сравнивается выход.

  | | остов FlowLM | LSD-голова | логит EOS |
  |---|---|---|---|
  | int8 per-tensor | 9.58% | 5.52% | 0.103 |
  | **int8 per-channel** | **8.44%** | **3.84%** | 0.103 |

  Отсюда дефолт — per-channel: он ближе к fp32 везде, а по LSD-голове на 30%, и
  именно она пишет микроструктуру кадра, которая слышна как тембр. Размер тот же
  (76.2 против 75.9 МБ), RTF тот же, порог EOS не сдвигается.

- **fp16 и bf16 на AVX2 бессмысленны.** У Zen 1 есть только F16C — конвертация
  fp16↔fp32, без арифметики, поэтому ORT кастует в fp32 и считает там. Замер на
  доминирующем GEMV 1×1024 @ 1024×1024: fp32 48.6 мкс, fp16 57.7 мкс. Половинной
  точности как компромисса между int8 и fp32 на этом железе не существует.
- **Лицензия весов не определена.** У `genvoice/xVibePocketTTS` на HuggingFace
  поле license отсутствует, указано лишь, что база Kyutai заявлена под CC BY 4.0.
  Для продакшена условия надо уточнять у GenVoice. Код здесь и у всех
  зависимостей — MIT/Apache, см. [NOTICE](NOTICE).
- Governor `schedutil` разгоняет загруженные ядра до 2.9 ГГц, но с задержкой,
  которая бьёт по TTFB. На проде стоит поставить `performance`.

## Структура

```
src/model/     bundle.json, состояния, токенизатор
src/engine/    backend.hpp (шов), engine.cpp (pocket), s3.cpp, фабрика
src/text/      ударения, нормализация, токенный чанкинг, текстовый путь s3,
               числительные
src/voice/     прогрев, реестр, safetensors
src/audio/     wav, ресемплер (Kaiser polyphase), mp3
src/numa/      топология, пиннинг, локальная аллокация
src/http/      сервер, OpenAI API, метрики
web/           консоль (Vite + TanStack Router, вшивается в бинарь)
accent/        сайдкар RUAccent
tools/export/  экспорт в ONNX и квантизация для pocket, fetch_s3.py для
               чекпоинтов, приходящих графами, референсный рантайм на Python
tools/bench/   нагрузка и WER/CER через ASR
```

`tools/export/pyrt.py` — референсная реализация того же пайплайна на Python. Она
существует, чтобы C++ было с чем сверять: текстовый слой уже сверен с ней токен
в токен.
